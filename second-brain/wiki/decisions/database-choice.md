## The decision as planned

**Aurora PostgreSQL Serverless v2 with pgvector** as the system of record and the
catalog vector index — relational data, vectors and row-level tenant security in
one place (PLAN.md §1 decision 7, §3.2). Alternatives named and rejected: Neon,
and Aurora DSQL (no pgvector).

## What is actually running

README.md:

- **Development**: a local `pgvector/pgvector:pg16` container on port 5434,
  "matching what runs in production".
- **Hosted**: **Neon** — the alternative PLAN.md listed and did not pick — used
  "when something outside your laptop needs to reach the data, such as a deployed
  demo".

The divergence is real and undiscussed in either document. The plausible reading:
Aurora is the destination for a system with enterprise tenants and per-tenant KMS
keys, while migration to AWS is a **named non-goal** for now (ROADMAP.md §4) and
nothing forces the move until an enterprise customer or scale requires it. The
deploy role is written and waiting. Recorded rather than resolved.

## The operational detail worth not rediscovering

Migrations must run against Neon's **direct** endpoint, not the `-pooler` one:
Alembic runs DDL in a transaction, and a pooled connection in transaction mode
cannot hold one reliably. Application traffic can use the pooled endpoint
(README.md). Change the scheme to `postgresql+psycopg`, keep `sslmode=require`.

Connectivity, pgvector and schema are checked by `scripts/check_database.py`.

## Alembic owns the schema

CLAUDE.md, Migrations — the rules that make the database the schema authority:

- **Always `alembic revision --autogenerate`**, then review and edit. Hand-written
  migrations miss Alembic metadata and drift from model state.
- **Always backward-compatible.** Safe: add nullable column, create table, add
  index. Unsafe: remove or rename a column, change a type — those need add,
  dual-write, backfill, switch reads, drop old.
- **Never hand-edit inside the `# ### commands auto generated by Alembic ###`
  markers.** Losing the markers is the signal a change was hand-typed. Re-generate
  against a scratch DB stamped to the prior revision and layer hand-written parts
  outside the markers.
- **Exactly one head, always.** `alembic heads` returns one line; resolve with
  `alembic merge heads`, never by editing `down_revision`.

Four migrations exist: initial catalog/profile/brand (`0641b9d871dc`), storefront
registry and ingestion runs (`2308ed5c51f7`), quarantine (`29d57d09d77d`), search
indexes (`a0f8614e62ba`).
